# DM 回复菜单式引导清理

本文说明 paotuan 如何抑制 DM 回复中的“菜单式行动引导”，让玩家在普通跑团回复里直接描述自己想做的事，而不是从 AI 给出的选项中挑一个。

## 目标

普通 DM 回复应该提供：

- 玩家角色能感知到的场景信息；
- 当前压力、风险和可能后果；
- 必要的规则或状态反馈；
- 一个开放的继续空间。

普通 DM 回复不应该把行动包装成菜单，例如：

- “你可以选择：1. 偷听 2. 敲门 3. 离开”
- “是继续观察？敲门？还是绕开？”
- “下一步？调查门缝。敲门试探。离开。”
- “你可以选择关注：门缝蓝光、地面血迹、屋内低语”

这些写法会把玩家的自由行动压成 DM 预设的几个选项，也可能通过“可关注项”提前剧透线索权重。

## 保留内容

清理只针对 DM 输出里的菜单式行动引导，不针对事实列表。以下内容应保留：

- 战斗顺序、轮次、行动状态；
- 掷骰结果、DC、成功失败；
- 角色状态、玩家列表、目标列表；
- 规则查询结果；
- token、debug、audit 等诊断输出；
- 未被包装成“你可以选择”的客观线索列表。

关键区别是：事实列表可以存在，要求玩家从事实列表中“选择关注/选择行动”的菜单式包装不应该存在。

## 玩家求助时的例外

如果玩家明确问“我现在能做什么”“给点提示”“有什么选项”“我能攻击谁”这类问题，插件允许给出更具体的帮助。

但求助不等于允许任意行动菜单。规则是：

- 玩家问可见目标时，可以列出玩家可见的目标；
- 玩家问提示时，可以给方向性帮助，但不应强迫玩家在编号选项里选择；
- 玩家没有问目标时，不应输出“攻击左边、右边还是锁”的目标菜单。

当目标不明确时，正确做法是要求玩家说明具体目标；只有已经存在明确上一个目标时，才可以沿用。DM 不应替玩家说“按当前局势裁定”。

## 实现边界

清理发生在 router 生成最终回复后、发送给 AstrBot 前。这样可以处理所有普通 DM completion，同时保留 router 中已有的诊断状态、玩家原始消息、provider 信息和 audit 上下文。

实现分两层：

1. 本地确定性规则先处理高置信度菜单，例如编号菜单、隐藏问句菜单和“下一步？”行动串。
2. 只有遇到尾部含义可疑但本地规则不够确定的短候选段时，才调用一次语义判断。

语义判断只做分类，不做重写。它只能判断候选尾部是否是给玩家提供多个行动/意图选项。最后的删除、保留或本地提示替换都由本地代码完成。

## 审计与隐私

插件会写入 audit 记录，说明是否发生了清理、清理原因、字符长度变化和文本 hash。

audit 不记录：

- 被删除的候选原文；
- 完整清理前回复；
- 完整清理后回复；
- 语义判断模型返回的原始 reason；
- 完整 prompt。

这样可以保留调试线索，同时减少把玩家文本或模型输出重复写进审计日志的风险。
